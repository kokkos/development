### Global Fencing on dealloc #9785
- We kind of promise that we fence on deallocs and we also don’t really do it (the PR is fixing this) do we want to promise that we do it and also spell that out in the documentation.
- Damien: When we only have accessibility from a certain space, we should only have a satic_fence. Otherwise we need a fence
- Daniel: we already fence too much, all host space deallocs are global fences
- How about HMM. Does that not make everything accessible? But when you do the allocation we can set the deleter. And since we cannot expand the accessibility we can infer the fencing need at that time.
- Daniel: But we do agree that we want to fence as not fencing at deallocation is considered a bug. We should promise that we fence every execution space that can access the allocation and that we can see.
- We could do it in the wake of looking into the SharedAllocationTracker

### MI300A team policy 
- Seems to indicate that a simple atomic (relaxed) is not enough to manage the scratch space. We seem to also need a memory fence or an atomic with acquire release.
- We currently do relaxed atomics on CUDA HIP and SYCL.
- Evan: there is a special register that tells you which sm you are in. Since they don’t get shared between kernels, we could use that if the acquire release is giving bad performance.
- We should do some perf testing and see if the acquire release actually does slow things down.
- But we do agree that this is a problem and should be fixed.
- Plan: extend pr to cuda and SYCL and do some perf measurements. Evan will talk to Mark and see if it is required in CUDA.
