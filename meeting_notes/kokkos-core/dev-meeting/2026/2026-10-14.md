Kokkos::Single (PR 8123)

Paul Gannay has addressed many of the concerns of Christian. He is working on the rest.
Christian and Damien are not blocking regarding the changes made from tools point of view. Damien just felt that the total number of changes is too much in the PR because of tools related changes.
Christian has made an analogy with respect to parallel_scan, which can either return a value or not. Thus the tools related changes for single should work.
On a related note, the macro regarding tool version number needs to be updated.

Avoid TypeInfo instantiation when label specified (PR 9653)

By Andrew Reisner. This avoids very long symbols in downstream applications, when the label is explicitly specified.
Daniel feels the total amount of change is too much. Damien briefly went over the implementation. It is nasty due to the ugly tools implementation. There are many places to change due to the various overloads of the parallel patterns.
Damien is opposed to CMake option based approach.

kokkos/mdspan 5.3 will also be released.

Christian wants to include as many C++26 features as possible. Some of them have been finalized relatively recently.
Main pending PR Add range_slice (#479).
Also, changing the directory structure and clang-format are planned.
According to Nic, some renaming also needs to be done.

NextSilicon TeamPolicy (PR 9594)

Carl Pearson feels it is ready to go. He also pointed out that a rebase is planned but not sure why.

std:float16_t and std::bfloat16_t in Kokkos::Experimental::[b]half_t (PR 9253)

Christian feels that for CPU only backends, this should always be the case. He wonders why the implementation cannot be based on this spirit. Daniel explained that the approach has unfortunately been different. We would like to know how does half_type behave on host. There used to be a time when only assignment was possible. Mark Hoemmen will clarify.
Overall, there is still work to be done. Damien feels it should be pursued without 5.3 being blocked on it.

Allow non-RDC desul atomics to be used in RDC code (PR 9346)

Evan Weinberg gave an overview of the PR. There are applications which use an existing Kokkos (that was built as non-RDC) and would like to run non-RDC desul atomics in code built as RDC. “A factory approach”.
Multi-GPU setting is not a concern. There are other issues anyway.
There are many user beyond PETSc.
According to Jakob, for other well-known atomic libraries lock-free atomics work out of the box. Desul should aim for it.
According to Christian, checking where an atomic variable is lock-free or not is a simple compile time check.
A CMake option in Desul (that will be passed on to Kokkos) was also discussed.
For this PR also, there is still work to be done. Damien feels it should not block 5.3.

HIP Multi-arch and amdgcnspirv offload target update (PR 9384)
Of course, not targeting 5.3.
Damien feels it is in the right direction. It will be useful for more recent devices.
Christian feels it should be merged to develop soon enough and tested with downstream applications.

Desul PR 179

Seyong Lee has been asked to look into atomic loads/stores for OpenACC.
Already done for several backends. However, OpenMP in desul is OpenMP-Target.
