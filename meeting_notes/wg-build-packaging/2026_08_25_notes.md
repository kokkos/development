 -Discussion about architectures that are listed in our spec but we error when they are concretized: 
   - Richard: At the moment we can change the logic to fail earlier and make the error more expliciy at concretization time. There is a PR incoming [#4416](https://github.com/spack/spack-packages/pull/4416) to help with this issue.
   - An alternative is [#5873](https://github.com/spack/spack-packages/pull/5873)
   - Problem: downstream packages that just loop over all archs that are in a `RocmPackage` or `CudaPackage` and depend on us will fail if we restrict the spec to the arches we actually support.
     On the other hand people that ask for archs like `90a` will currently only see a failure when our package spec gets concretized.

- Deprecated code:
  - Basically, we want to mirror what cmake does (a transition period defined by default values)
  - Therefore, we need to extend the option that we allow for deprecated code (proposal: `all` `none` `auto` `previous` `current`)
  - We are in favor of just yanking the old binary option and replacing it with the new one without a transition period. If someone is still using the old one they should stay on an older version of spack and transition. For all packages that we see using this option, we can include the change in the pr.
  - Richard has an old pr that can be revived for that
